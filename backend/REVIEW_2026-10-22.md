## 2. 数据流：一股字节，两个消费者

### 2.1 上行

> ⚠️ 本节为 2026-10-22 架构快照：`scan_dir_frames`/`_dir_cache`/RxEvent 事件链/`_on_serial_event` 已于 2026-10-23 傍晚重构删除，目录帧改经 `hub._on_frame(cmd, payload)` 入库 `DirEntry{item, frame}`（见页眉注记与解析文档 0.3 节）。

```
V5 User 口 ──► SerialBridge._rx_loop（线程 vex-serial-rx，2ms 轮询 in_waiting）
                 │
                 ├─① on_raw(chunk) ──► Hub._on_serial_raw（hub.py:666）
                 │     ├─ _broadcast_bytes：原样推给所有 WS 客户端（前端 FrameParser 自己拆，零改动）
                 │     └─ scan_dir_frames 旁路摘目录帧 → _dir_cache 原始帧缓存（供回放）
                 │
                 └─② parser.feed(chunk) ──► FrameParser 状态机 ──► RxEvent
                       └─ Hub._on_serial_event（hub.py:688）按 isinstance 分派：
                            DirectoryEvent → 三张目录表 + 名字反查 + monitor_latest 初值
                            CmdDirectoryEvent → 命令表 + 认出停车命令（tag SPEC=Stop）
                            ValueEvent → monitor_latest 快照 +（logging 且已登记）_record 落样本
                            EchoEvent → 回写调参项真实生效值
                            PongEvent → 时间戳在 bridge 里已更新
```

**目录有三份表示**，各有理由：结构化表（`monitor_dir` 等，供 /api/column 与解析）、原始帧缓存（`_dir_cache`，供 WS 字节级回放）、前端自己解（透传字节）。这是"前端代码与直连串口时代零改动"的代价，设计上成立。

### 2.2 下行：唯一优先级队列

```
UI 帧（from_ui）────────┐
脚本命令（hub.cmd）──────┤
订阅 diff / 目录请求 ────┤► enqueue(frame, priority)（hub.py:742）
紧急停车 ────────────────┘        │
                                  ▼
                    _tx_q：按 (priority, seq) 排序
                    STOP=0 < UI=10 < SCRIPT=20
                                  │
                          唯一写线程 vex-tx（_tx_loop，hub.py:757）
                                  │
                    bridge.send() ──► 串口（bridge 内 _tx_lock 串行化）
```

三个值得知道的行为：

- **停车不等串口**：`emergency_stop`（hub.py:1187）做三件事——置 abort、清队列里所有 PRI_SCRIPT 帧（保留 PRI_UI）、以 PRI_STOP 插队。断线时 STOP 帧被 `appendleft` 塞回队首每 0.5s 重试，tx 线程被它独占直到发出（hub.py:771-778，注释自证是有意的）。
- **diff 后才发订阅**：`_recompute_and_emit`（hub.py:857）比对聚合意图与 `fw_sub`，不变不发包。
- **断线时非 STOP 帧直接丢**（hub.py:769-778），不报错不重试。

### 2.3 订阅意图聚合（设计亮点）

`_sub_intent: {index → {source → (sub, fast)}}`，source 是 `ui:{id(ws)}` 或 `"script"`。聚合规则（hub.py:575-585）：sub 取并集；fast 取**已订阅者中**的最高档（`any(v[1] for v in intent.values() if v[0])`——没订阅的人要什么档位都不算数）。效果：A 页面退订不会把 B 页面的高速推送降级；页面断开走 `_drop_client_intent` 只清自己的 source。重连后 `_restore_subscriptions` 按意图补发，做到"重连不丢订阅"。

### 2.4 记录会话

一段 = 一次 `start_log → end_log`。时间戳用**下位机采样时刻**（`_expand_stamp` 把 uint16 回绕展开成连续毫秒，hub.py:1270），不是 PC 到达时刻——扫参/微分不受 USB 批量到达和本机调度抖动影响，这是对的选择。样本只记"已登记项"（`log_reg`），未登记的高频项不进内存；超 50 万条丢新不丢旧。

## 3. 线程与锁模型

| 线程 | 职责 | 退出方式 |
|---|---|---|
| 主事件循环 | FastAPI + WS 收发 + HTTP | lifespan |
| `vex-serial-rx` | 收数轮询 + 喂解析器 + 广播 | `_stop` 事件 |
| `vex-tx` | 唯一串口写者，睡 Condition | `_running=False` + notify_all |
| `vex-heartbeat` | 80ms 一拍 Ping，1s 无 Pong 判掉线 | `_hb_stop` |
| `vex-connect` | 启动时一次性探测（auto_connect） | 自然结束 |
| `vex-reconnect` | 掉线后每 5s 重试，连上即退 | 连上 / `_want_connected=False` |

| 锁 | 保护对象 | 备注 |
|---|---|---|
| `_tx_lock`（bridge） | 串口 write 串行化 | tx 线程与心跳线程都调 send |
| `_tx_cv`（hub） | `_tx_q` + tx 线程睡眠/唤醒 | 兼两职 |
| `_sub_lock` | `_sub_intent` / `fw_sub` | 三个并发来源：事件循环、HTTP 线程池、重连线程 |
| `_log_lock` | `log_dir` / logging / `_log_stamp0` | rx 100Hz append vs HTTP 取样本/清空 |
| `_ws_lock` | `_ws_clients` | 事件循环 add/discard vs rx 线程广播前 list() 快照 |

**锁序检查**：所有路径都是 `_sub_lock → _tx_cv`（sub/from_ui/_drop_client_intent → _recompute_and_emit → enqueue），无反向获取，无死锁。`_lost` 从 rx/心跳线程调进来时不 join 自己（serial_bridge.py:320/398），处理正确。

**重连顺序安全性**（核对过）：`_reconnect_loop`（hub.py:535）清目录 → `_request_all_dirs`（同优先级同 seq 序，请求先发）→ 目录 burst 到达时重建类型表和 `monitor_latest` → 才 `_restore_subscriptions`。固件重启后订阅表为空，不会在类型表重建前推值，顺序上安全。

#### P1-2 协议层对非数值参数静默编 0

- **事实**：`protocol.py:185`（`encode_value8`）：`n = float(value) if isinstance(value, (int, float)) else 0.0`。`/api/cmd` 的 `args: list[Any]`（main.py:118），JSON 里传 `"6.0"`（字符串）/ `null` / 列表，都会被编成 **0 帧**发给车。
- **场景（按本车命令表核实，robot_and_control.cpp:170-178）**：7 条命令中 4 条带 RANGE（直行/局部移动/设置电机电压/设置底盘目标速度），字符串参数会被范围检查拦下 → 400；**3 条不带 RANGE**（`原地转向`、`重置底盘位置`；停止运动无参）——`v.cmd("原地转向", "90")` 车里收到 0 度，HTTP 200 ok:true，不报错。`set_tunable_value`（hub.py:1250）则**完全没有任何类型校验**，对数值型调参项传 `"3.5"` 同样静默写 0。
- **校验缺口**：`hub.cmd` 的数值检查（hub.py:1243）只在字段带 RANGE（min/max）时触发；无范围字段完全不检查类型。
- **现状缓解**：`BackendLink.set_volt/drive_volt/spin_target` 都做了 `float()` 强转（script_api.py:591/598-599/603），便利层安全；**裸 `VexScript.cmd` 暴露此坑**。
- **修法**（建议都做）：① `hub.cmd` 把 isinstance 数值检查提升到所有字段（不管有没有范围），报 400 说清楚哪个参数不是数；`set_tunable_value` 按 `item.type` 补同样校验（Color 型按 `#RRGGBB` 放行字符串）；② `encode_value8` 对 str 先试 `float()`，失败抛 `ValueError`——让错误显式化而不是静默归零。

> **✅ 已修复（2026-10-22 晚）——但修法②被用户否掉，此处认账**：原提案②"`encode_value8` 对 str 先试 `float()`"是**方向错误**——它让最底层更宽容，把类型混淆往深处推。用户的判断是对的：**要么入口只能出字符串（GET query），那就在入口转；要么入口能出数字（JSON body），那就早早要求数字**。没有第三条路让字符串一路坐到编帧层。实际实施：
> - **边界**（第一道，400）：新增 `hub._check_field_type(what, ftype, value)`，按目录字段声明类型校验——数值字段（含 Bool/OnOff）只收 int/float，Color 字段只收 `#RRGGBB` 字符串；bool 是 int 子类，仅开关字段放行。`hub.cmd` 对**每个**字段调用（原来只在带 RANGE 时查），`set_tunable_value` 按 `item.type` 调用。Color 字段跳过大小比较（它的 min/max 解出来是颜色串）。
> - **编帧层**（纵深防御，抛错不静默 0）：`encode_value8` 重写——Color 走独立分支（非 str 抛 TypeError、非 6 位十六进制抛 ValueError）；数值分支对 str/None/列表抛 TypeError。正常不可达（边界已挡），真到达说明有校验缺口，应该是 500 而不是静默 0。
> - **一致性**：拆掉 `BackendLink.set_volt/spin_target` 的 `int()`/`float()` 偷偷强转——否则同一个逻辑调用，脚本通道放行字符串、HTTP 通道 400，行为不一致。全仓 grep 确认 7 个标定脚本的调用方传的都是数字（`motor_id()` 返回 int）。
> - **前端同修**：TS `encodeValue8` 有同款 `typeof value === 'number' ? value : 0`，且因此把 `true` 编成 **0**（Python 侧编 1，两边不一致）——已按同样纪律重写，`vue-tsc` 类型检查零错误。
> - **测试**：`test_protocol` 新增 `test_encode_rejects_non_numeric` / `test_encode_color`；`test_hub_proxy` 新增 cmd 字符串/布尔拒绝、set_tunable 字符串拒绝、int 放行用例。
> - **行为变化提示**：原本"静默成功"的错误调用现在明确报 400（例：`v.cmd("原地转向", "90")` → `命令 原地转向 的参数 角度 需要数值(int/float)，实际给了 str: '90'`）。老脚本若依赖静默 0 行为会在这里暴露——这正是目的。

#### P2-1 跨线程迭代字典：三处竞态，500 而不是正确的 404/200

- **main.py:353** `for idx, s in hub.monitor_latest.items()`：rx 线程在目录 burst 到达时向 `monitor_latest` **插入新 key**（hub.py:535），HTTP 线程同时迭代 → `RuntimeError: dictionary changed size during iteration` → `/api/values` 返回 500。触发窗口：连接后首批目录 burst 与前端轮询 `/api/values` 撞上（connect → 拉表 → 轮询是标准时序，完全可能）。
- **hub.py:873 / 893 / 912**：`resolve_monitor / resolve_tunable / resolve_cmd` 的"忽略大小写容错"循环遍历 `_name_to_*`，rx 线程写同一 dict（hub.py:534/545/551）。注意该循环只在**精确匹配失败时**才走到（ typo、数字字符串不在表里等 404 路径）——所以现象是：一个本该干净 404 的请求，若恰逢目录 burst，变成 500。
- **不变量说明**（为什么 ValueEvent 不插 key）：类型表登记与 DirectoryEvent 在 rx 线程同一顺序处理中成对出现，ValueEvent 到达时 key 必已存在——所以迭代崩溃只源自目录事件插 key。但这个不变量**没有任何注释在 main.py:353 处标明**，读代码的人无从判断安全与否。
- **修法**：三处包 `list()`，一行一处，零风险：`list(hub.monitor_latest.items())`、`list(self._name_to_mon.items())` 等。

#### P2-2 MonitorValue 空帧让状态机假死并误记 overflow

- **事实**：`protocol.py:443-445`：`if self.payload[0] > 0: self.expect = 1 + self.payload[0]`。`payload[0]==0`（无项的推送帧）时 `expect` 永远为 -1，状态机一路吃到 `MAX_PAYLOAD` 记一次 `overflow` 回找帧头。
- **背景核实（2026-10-22 晚，communication.cpp:385-438）**：`monitor_tick` 只在 `pack_num > 0` 时才 flush，且每帧必含 2B 时间戳——**真实帧的 payloadlen ≥ 2，固件永远发不出 payloadlen=0 的帧**。所以健康链路上这个分支不可达；只有流错位时（上个帧 XOR 失败后把 payload 里的 0xA5 当帧头、0x02 当命令字，随后那个"长度字节"实际是数据且恰好为 0）才中招：吞掉后续约 445 字节真数据 + 虚记 1 次 overflow（overflow 是前端 UI 直接读的链路诊断计数，虚高会把排查带偏）。
- **TS 同构**：`protocol.ts:545` 一字不差同样的 `> 0` 判断——修要两边一起修。
- **修法**：去掉 `> 0` 判断，直接 `self.expect = 1 + self.payload[0]`。payload[0]==0 时期望=1，收满 1 字节进 WaitXor，xor 校验几乎必然失败（需碰巧 `0x02^0x00` 对上）→ badChecksum 回找帧头，3 字节完成干净重同步；dispatcher 里 MonitorValue 有 `len<3` 早退兜底。TunableEcho 分支本来就允许 expect=1（类型查不到时 value_size=0），行为一致。

> **✅ 已修复（2026-10-22 晚）——采用了用户提出的更优方案**：用户指出"payload[0]==0 时说明出错了，直接找下一个帧头才对"，比上述"猜 expect=1"更好：**0 长度对 MonitorValue 非法（固件永远发不出），那这个 A5/02 帧头对本身就是错的，没有理由再猜长度**。实际改动：`payload[0]==0` 直接 `state = WaitHead` 回找帧头——比 expect=1 方案少吞 2 字节，且杜绝了"碰巧 xor 通过产出脏帧"的 1/256 概率（虽有 `len<3` 兜底）。protocol.py 与 protocol.ts:543 同步修改；新增测试 `test_parser_monitor_value_zero_len_resyncs`（喂 `A5 02 00` + 正常 Pong，断言 Pong 被解出且 `overflow==0`——旧代码下 Pong 会被吞掉）。

#### P2-3 `calc()` 表达式白名单两处小瑕疵

- **死条件**：hub.py:1260 `if n not in self._name_to_mon and not isinstance(n, str)`——`ast.Name.id` 必为 str，后半永假，整个判断永假；真正校验在 hub.py:856 起的 `resolve_monitor`。建议删掉，别留误导。
- **字符串常量漏网**：hub.py:1266 放行 `ast.Constant` 不限类型，`"左0转速 + 'abc'"` 能过白名单，到 hub.py:1267 `float(node.value)` 抛 ValueError → 400。结果可接受但不干净；白名单节点检查里加 `isinstance(node.value, (int, float))` 更严。
- 白名单整体是可靠的（无 eval，函数调用/属性/比较/下标全部拒绝），以上只是打磨。

> **✅ 已修复（2026-10-23 凌晨）**：两处都改了——死条件循环删除（`resolve_monitor` 本来就抛 KeyError）；`ast.Constant` 分支只收 int/float，bool/str/None/列表明确报"表达式里只允许数值常量"（bool 与数值字段的纪律一致：当数值传几乎总是笔误）。
>
> **⚠️ 修复过程暴露了一个更严重的漏洞（审查遗漏，在此认账）**：初版白名单只放行了 `Name/BinOp/UnaryOp/Constant/Expression`，漏了 **`ast.walk` 会把运算符节点（`Add`/`Sub`/`Mul`…）和上下文节点（`Load`）也吐出来**——导致**任何表达式都过不了校验**：`calc("左0电流 - 左1电流")` 甚至 `calc("左0电流")`（Name 自带 `ctx=Load` 子节点）都会 400"表达式只允许监控项名、数字和 + - * / ** 运算"。该代码在未提交的工作区改动里、从未被成功执行过（`pytest/_test_calc.py` 6 个调用全带运算符），所以没被发现。**修法**：放行元组补 `ast.operator, ast.expr_context` 两类基类；新增端到端用例（4.4：造两段样本跑 `x - y` 的 mean/sum/逐点序列/window 子区间/单值项混算），保证这类"整体不可达" bug 有测试兜底。**教训：白名单类校验必须配一个"合法输入能完整跑通"的用例，只测拒绝路径等于没测。**

> **⚠️ 上述修法自身引入了回归（2026-10-23 凌晨二次修复，已修）**：放行 `ast.operator` **基类**等于放行了它的全部子类，而 `Mod(%)` / `FloorDiv(//)` / `LShift` / `RShift` / `BitAnd` / `BitOr` / `BitXor` 全是 `ast.operator` 子类却**不在 `ops` 表**里 → 白名单照放，到 `eval_node` 的 `ops[type(node.op)]` 才抛 **KeyError** → `main.py:302` 把 KeyError 一律转 **404**，于是 `calc("x % 2")` 伪装成"监控项不存在"（detail 是 `<class 'ast.Mod'>`）。旧白名单反而把它们挡成 400，语义正确。**修法**：放行元组由 `ast.operator` 改为 `*ops`（只放行真正实现的运算符）。
>
> 同批修掉的两处 500 风险：`ast.Pow` 可产出**复数**（`(-8) ** 0.5` → complex，混进聚合后 JSON 序列化炸）与 `OverflowError`（`2.0 ** 10000`，非 ValueError/KeyError，直通 500）。**修法**：新增 `as_real()` 收口，复数/inf/nan 与溢出就地转 ValueError(400)；除零不在此挡（数据问题，逐点跳点更合适）。另删死字段 `_CALC_OPS`（全仓无读写），并把"没有可配对的有效点"的错误文案补上窗口无样本/某项无取值两种真实成因。新增用例 4.5（未支持运算符一律 400，连 KeyError 一起断言防回归）、4.6（复数/溢出就地报错）。**教训：放行"基类"的白名单等于放行未知实现，白名单必须与能力表同源。**

> **第二轮调研（2026-10-23 凌晨，含一条自我推翻）**
>
> - **❌ 撤回"基准项 `sorted(seq)[0]` 导致静默丢样本"的判断**（上一版我判为高危，实测证明是错的）：有效点数由 `if not all(n in env for n in names): continue` 决定，即**各项同拍交集**，与谁是基准无关。三组实测（1点 vs 5点、3点 vs 5点、10ms vs 5ms 采样率）基准取多项/少项结果完全相同（n = 1/1、3/3、4/4）。已加 4.10 用例固化这个事实，防止以后误改。**教训：看到 n 变小就归因于"索引骨架"，没有先验证"交集才是上限"。**

### P4：设计观察 / 可选优化（5 条，不着急）

1. **enqueue 每次全量排序**（hub.py:748-755）：`deque(sorted(...))` 每帧 O(n log n)，代码注释已自认。由于 seq 单调递增，新帧只在"优先级低于队中某帧"时才需要重排——可优化为 `priority >= 队尾 priority 就直接 append，否则 sorted`。队列通常几帧，只有 100Hz 高频下发（set_volt 扫参）才值得动。
2. **`log_samples()` 每条样本 O(项数)**（hub.py:1296 调用，1301-1305 实现）：100Hz × 20 项 = 每秒 2000 次字典遍历求和。维护一个 `self._log_count` 计数器即可，同样属于"量大了才疼"。
3. **script_api 对命令表有命名耦合**：`stop_move / set_volt / spin_target` 硬编码中文名 "停止运动" / "设置电机电压" / "设置底盘目标速度"（script_api.py:180/591/603）。hub 层停车是按 tag SPEC 位 + 目录认的（protocol.py:114-120），script_api 却按名字——与 README"后端不认识任何命名约定"的哲学有摩擦。换固件表名时这里有 404 兜底不会静默错，但建议失败时报清楚"命令目录里没有 X，当前目录有：..."。
4. **协议边界逻辑三处实现**：TS FrameParser（前端）、`protocol.FrameParser`（Python）、`scan_dir_frames`（protocol.py:313-354，hub 旁路缓存用的线性扫描）。三者必须与 C 侧 `communication.h` 同步——protocol.py 文件头已警告。`scan_dir_frames` 只认目录帧、靠长度试算 + 校验兜底，目前工作正常，但它是第三份会腐烂的代码；长期看值得把"帧边界切分"抽成一处、解析策略各自注入。
5. **`from_ui` 里两处 `run_coroutine_threadsafe` 是绕圈**（hub.py:897/916）：`from_ui` 只被 `attach_ui` 的 receive 循环调用（hub.py:804/815），本身就跑在事件循环线程，Ping 代答和目录回放可以直接 `await ws.send_bytes(...)`。功能正确，纯粹是多余一层调度。
